## 1. 版本矩阵（先抄这张表，别凭记忆）

| 组件 | 本项目验证版本 | 关键约束 |
| --- | --- | --- |
| Minecraft | 1.20.1 | 与 Forge / mod / minecraft-data 三方必须对齐 |
| Forge | 1.20.1-**47.4.x** | 47 系适配 1.20.1；换小版本问题不大，别跨大版本 |
| Java | **17** | Forge 1.20.1 要求 17；21 可能起不来或 mod 异常 |
| Node.js | 22.x | 20 也可；22 注意 `@discordjs/opus` 无预编译包（见 §10） |
| Python | 3.10+ | 仅语音链路需要 |
| Simple Voice Chat | **2.5.x（协议 18）** | ⚠️ 见下表，锁版本最稳 |
| mineflayer-simplevoice | 原生对应协议 18 | 与服务端 SVC 必须同协议 |

### SVC 协议版本映射（错一位就连不上）

```
2.4.x → 协议 17
2.5.x → 协议 18     ← mineflayer-simplevoice 原生对应
2.6.x → 协议 20
```

**现象**：bot 能进服、能打字，但语音模块一连接就被踢或静默失败。
**根因**：协议版本号不匹配，服务端直接拒绝握手。
**处置**：**服务端与客户端统一锁 2.5.x**。不要"顺手升到最新"。

### 同一条铁律的其他分身

- **客户端 mods 与服务端 mods 必须一致**：不一致时 Forge 只给一条 `Received unexpected index 0 in client reply` 之类的 FML 握手警告，**不致命但说明有分歧**。一旦将来连不上，优先查这里。
- **`minecraft_version` 写 `"auto"`**：让 minecraft-data 自己探测，比手写更不容易错。
- **换 MC 版本 ≠ 改个数字**：`server.jar` / mods / minecraft-data / SVC 四条链要一起动。

## 2. 服务端搭建顺序（照做即可）

1. **装 Forge**：跑官方 installer，选 `install server`，生成 `libraries/` 与 `run.bat` / `win_args.txt`。
   - ⚠️ Forge 服务端**没有 `server.jar`**，靠 `libraries/` + `win_args.txt` 启动。**"找不到 server.jar" 不是故障，别去补。**
2. **写 `eula.txt`**：`eula=true`（首次启动也会自动生成，直接改）。
3. **配 `server.properties`**（关键项）：

   ```properties
   server-port=25565
   online-mode=false          # bot 走离线 UUID；开着会让 bot 进不来
   enable-rcon=true
   rcon.port=25575
   rcon.password=<自己设一个强密码>
   broadcast-rcon-to-ops=false
   level-name=world
   gamemode=survival
   difficulty=normal
   max-players=20
   view-distance=10
   allow-flight=false
   ```

   > 资源包**不要**在 `resource-pack=` 里配 —— 服务端推送资源包会拖慢每个玩家进服，且和语音 mod 无关。
4. **装 mods**：全部丢进 `mods/`。见 `server/mods_list.txt`。
   - 服务端 mod 与客户端 mod 不是一回事，**只装服务端必需的那些**（家具/储物/语音等纯客户端增强可不装）。
5. **首次启动**：让服务端把 `world/` 生成完整，再动任何东西。
6. **语音 mod 配置**：`config/voicechat/voicechat-server.properties` 里的 `voice_host` —— **见 §10，多数情况留空**。
7. **防火墙**：放行 25565/TCP。RCON 25575 **只给本机用**，不要对外暴露。
8. **给 JVM 分内存**：`user_jvm_args.txt` 里 `-Xmx` 建议 **4G~6G**（16G 机器上留足给客户端）。样例见 `server/user_jvm_args.txt`。
9. **启动脚本**：包一层 bat/sh，把 `cd` 到服务端目录再启动，**并把 stdout 重定向进日志文件** —— 出问题时日志是唯一线索。

### 首次启动会很慢，别误判为卡死

- 第一次要生成地形、加载全部 mod，**3~10 分钟都正常**。
- 判断"起来没有"的唯一可靠信号是 **端口 + RCON**（§8），不是控制台刷到哪一行。

## 3. 端口与网络清单

| 端口 | 协议 | 用途 | 对外暴露 |
| --- | --- | --- | --- |
| 25565 | TCP | 游戏本体 | ✅ 需要 |
| 25575 | TCP | RCON 管理 | ❌ **只给本机** |
| 24454 | **UDP** | Simple Voice Chat 语音 | ✅ 外网联机时需要 |
| 8080 | TCP | Mindcraft bot 网页控制台 | ❌ 本机 |

**两个高频误判**：

- **语音是 UDP**。只做 TCP 端口检测会觉得"语音端口没开"，其实一切正常；反过来只放行 TCP 也会导致语音不通。
- **bot 控制台可能只绑 IPv6 回环（`::1`）**。
  **现象**：`127.0.0.1:8080` 连不上，以为 bot 没启动。
  **根因**：监听在 `::1`，IPv4 回环不通。
  **处置**：浏览器一律用 **`localhost:8080`**（会走 `::1`）；脚本检查端口时**IPv4/IPv6 都要试**。

## 4. RCON 使用规约（Agent 必读）

RCON 是给机器用的管理通道，比在游戏里打字快得多，也危险得多。

### 4.1 协议要点

- **必须先发认证包**：包 id=1、type=3、body=密码。**不发认证直接发命令，服务端不响应**（表现为"命令没效果"，很容易误判成权限问题）。
- 应答包顺序与请求 `id` 对应，实现批量时要自己配对。
- 少量命令用命令行工具，**大批量（几十条以上）走"命令文件"**：一行一条，`#` 开头为注释。这样可复现、可复核、可重跑。

### 4.2 ⚠️ `sendCommandFeedback` 永远保持 false

这是本项目**代价最大的一次事故**，单独成条：

```mcfunction
gamerule sendCommandFeedback false
gamerule commandBlockOutput false
gamerule logAdminCommands true
```

**事故链**（打开后发生的事）：

1. 每条 RCON 指令的执行结果（`Summoned new Item Frame` 之类）**被广播进聊天栏**；
2. 如果有 AI bot 挂在服务器上，它把聊天栏当"玩家说的话"**逐条喂给大模型**；
3. 结果是：**疯狂烧 token** + **bot 开始自主乱动、破坏正在施工的工地**；
4. bot 的记忆文件被这些噪音永久污染，事后还要手工清理。

**两个必须记住的点**：

- **排查时也不需要打开它**。`execute if block ...` 这类命令**返回值不受该 gamerule 影响**，照常返回 `Test passed/failed`；老老实实读 RCON 返回值就够了。
- 它的名字看起来像"调试开关"，实际是"**把服务端日志灌进所有人聊天栏**"。默认就该是 `false`。

### 4.3 其他 RCON 注意事项

- **`op` 不等于能执行一切**：部分命令受 gamerule / 权限等级限制，失败时先查 gamerule 再怀疑权限。
- **RCON 不加载地图就不给干活**：远距离施工前先 `forceload add`（§5）。
- **不要用 RCON 做破坏性操作而不留痕**：批量命令先写进文件、提交或备份，出问题能复盘。

## 5. 世界操作与施工（省 token 的正道）

如果用 LLM 驱动 bot 去盖房子，**不要让它写代码逐块放**——慢、贵、且几乎必然出错。

**正确做法**：由外部脚本生成 `/fill`、`/setblock` 命令，经 RCON 批量下发。

| 事项 | 做法 |
| --- | --- |
| 大范围建造 | `/fill x1 y1 z1 x2 y2 z2 <block>`，一次几十~几百格 |
| 远处施工 | 先 `forceload add <x> <z>`，否则报 "position is not loaded"；完工 `forceload remove all` |
| 清空区域 | `fill ... air`（注意**别把相邻结构一起清掉**，本项目就误埋过一整层家具） |
| 一次性完工 | 命令按"先结构后装修"排序，**避免后面的 fill 覆盖前面的精细摆设** |

### 验收：不要靠"看起来"

1. **先 `save-all flush`** 把内存写盘；
2. 再 **离线直读存档**（读 `.mca`，不需要服务端在线）逐个检查点验证方块；
3. 或 **实时统计**：用计分板/统计器数实体个数（静态读存档在区块边界会重复计数，**实体数量一律以实时统计为准**）。

**只截图/只肉眼看 = 不算验收。**

## 6. 坐标与 NBT 的两个铁律

### 6.1 悬挂实体坐标 = 支撑方块坐标 + 1 + 0.03125

**现象**：`summon item_frame` 之后，**约 5 秒实体自行消失，不掉落、不留任何痕迹**，日志里也没有明显报错。极难排查。

**根因**：坐标算错，实体被塞进墙里 → 服务端判定"支撑无效" → 自动销毁。

**规则**：

```
支撑方块 x = -443
展示框 x   = -443 + 1 + 0.03125 = -441.96875   ✅
           = -443 + 1 - 0.03125 = -442.03125   ❌ 5 秒后消失
           = -442.5（块中心）                    ❌ 5 秒后消失
```

- 朝 **+x / +z** 方向 → 偏移 `+0.03125`；朝 **-x / -z** 方向 → `-0.03125`。
- 贴墙悬挂物**只用这一种算法**，别自己推。

### 6.2 NBT 键名大小写不统一

| 实体 | 朝向键 | 取值 |
| --- | --- | --- |
| `item_frame` | **大写** `Facing` | 0下 1上 2北 3南 4西 5东 |
| `painting` | **小写** `facing` | 0南 1西 2北 3东 |

壁画 1 格高时 `y = 格y + 0.5`。

### 6.3 mod 方块/物品 ID

- **不要带 `minecraft:` 前缀**。带前缀的 mod 物品多半解析失败。
- 拿不准 ID 就先 `/give` 试一次，或查 mod 的 jar 内 `assets/<modid>/`。

## 7. 模组加载与版本检查

### 7.1 先说最重要的一条

**Forge 服务端从来不会自动下载或替换 `mods/*.jar`。**
所谓"版本检查"= 联网查一下 + 打印一行字，**没有任何自动升级机制**。"保持当前版本"就是默认状态。

### 7.2 Forge 统一版本检查 → 可以关

`config/fml.toml`：

```toml
#Enable forge global version checking
versionCheck = false
```

**现象**：每次启动日志里一堆 `[Forge Version Check]`，还把某些 mod 标成 `OUTDATED`（本项目 11 个 mod 被逐个检查）。
**处置**：改 `false` 后**一个都不会再跑**，日志清净，也不会再有"某 mod 有新版本"的误导性提示。

### 7.3 各 mod 自带的检查器 → 看情况，有的关不掉

以 **Iron Furnaces** 为例：它的 `ThreadUpdateChecker` **直接把版本文件 URL 硬编码在字节码里**，`openStream()` 无条件拉取，**不读任何配置项** → 服务端侧**没有开关可关**。

- 它目录里那个 `[misc] web` 开关属于 **CLIENT 配置**，服务端压根不加载 —— 改了白改，别浪费时间。
- **好消息**：拉不通就是拉不通，**拿不到新版信息 → 不弹提示 → 不换文件**，只在日志里留几行 ERROR。**无害。**

### 7.4 会被误当成"服务器坏了"的启动阻塞

**现象**：启动比平时慢 5 分钟，日志停在一个下载/校验动作上不动。
**案例（本项目）**：自动汉化更新 mod 每次启动会比对本地与远端汉化包的 **MD5**，不匹配就重下；远端**可达但传输极慢**，每个包耗 100 秒超时，三个包共 **300 秒**。
**关键**：下载失败后它会**自动回退用旧包**，功能不受影响 —— **纯粹白等**。
**处置**：属于外部原因，知道就好。**不要把等待超时当成启动失败**，更不要在此时去重启（会产生多个服务端实例抢端口）。

### 7.5 排障手法

```bash
# 有没有加载失败
grep -iE "failed to load|missing or unsupported|Incompatible mod set" server_console.log
# 崩溃报告
ls crash-reports/          # 不存在 = 没崩过
# ERROR 的性质（逐条看，多半是联网类噪音）
grep -i "ERROR" server_console.log | sort | uniq -c | sort -rn
```

**判断标准**：**33 条 ERROR 里 32 条是联网检查失败 ≠ 服务器有问题。** 先归类再下结论。

## 8. 进程托管与"服务真的起来了吗"

### 8.1 进程为什么会被"莫名其妙杀掉"

如果你在**受管理的会话/沙箱环境**里启动服务（自动化 Agent、IDE 内置终端、某些 CI）：

- 每条命令可能被包进一个 **Job Object**，**命令一结束，整个子进程树被连带终止**；
- 已实测**无效**的方式：`DETACHED_PROCESS`、`CREATE_NEW_CONSOLE`、`CREATE_NO_WINDOW`、新进程组；
- `CREATE_BREAKAWAY_FROM_JOB` 常因 Job 未授权而**创建即失败**（`winerror=5`）。

**唯一可靠**：用环境自带的**受管理的后台任务**机制，或者干脆注册成 **Windows 计划任务 / 系统服务 / `nssm`**。桌面双击启动也行（进程归 Explorer，不受会话影响）。

> 结论：**不要试图用"分离进程"绕过托管**。要么用平台给的后台任务，要么落成服务。

### 8.2 守护进程要能自己判断"该不该活着"

一个能用的 watchdog/守护脚本应该：

1. 定时轮询**端口**（不是只查进程名）；
2. **所有被托管的服务都退出后，守护自己退出**（否则永远留一个空转进程）；
3. 启动子服务前**先判断是否已在运行**（否则重复拉起 → 端口冲突）。

### 8.3 判断进程/端口的工具坑

| 坑 | 处置 |
| --- | --- |
| `tasklist /fi "imagename eq X"` 在某些环境**恒返空** | 用**全量列表**再自己过滤，别信 `/FI` |
| PowerShell 调用拿不到 stdout（只回 exit code） | 改用 Python + `psutil` 查询进程/父子关系/端口 |
| `taskkill /F /PID` 在某些 shell 里参数被转义（`/F` → `F:/`）报"无效参数" | 用 `psutil.Process(pid).kill()` |
| 想确认"服务端是不是我启的那个" | 查**进程 cwd + 监听端口**，别只看进程名（同机可能还有别的 java） |

**进程归属原则**：**只关你自己启动的进程**。用「命令行 + 工作目录 + 监听端口」三者交叉确认，再动手。

### 8.4 ⚠️ 启动顺序：服务端就绪了再起 bot

**现象**：bot 日志 `Error: connect ECONNREFUSED 127.0.0.1:25565`，随后 `Agent process exited with code 1 → too quickly and will not be restarted`。
**根因**：服务端还在加载（例如卡在 §7.4 的下载），bot 去连被拒；**Mindcraft 的 agent 子进程不会自愈**。
**更麻烦的**：bot 的**主进程（MindServer）仍活着并占着 8080**，此时重跑启动脚本会被判"已在运行"而跳过 → 看起来"启动了"其实根本没连上。

**处置**：

```
就绪判据 = 端口开放 AND RCON 能应答
```

- 等待上限设**足够长**（本项目从 120 秒放宽到 600 秒），并**超时后不要盲目启动 bot**；
- 每次启动后**用 `RCON list` 确认 bot 真的在线**，不要只看进程在不在；
- 万一已经卡死：**杀掉残留的 `node main.js` 释放 8080 → 再启动一次**（会跳过已在跑的服务端，只拉 bot）。

## 9. 接入 AI bot（用 mineflayer 进 Forge 服）

| 配置 | 值 | 说明 |
| --- | --- | --- |
| `forge_server` | `true` | **只在 Forge 服务端开**；连原版服务器必须 `false` |
| `host` / `port` | 服务器 IP / 25565 | |
| `auth` | `offline` | 服务端 `online-mode=false` 时必须 |
| `minecraft_version` | `"auto"` | 别手写 |
| `forge_mods` | `[]` | 一般留空；服务端校验严时才与服务端 mod 列表对齐 |

**其他要点**：

- **掉线不会自动重连**，服务端重启后必须重启 bot 主程序（或用 §8.2 那种守护）。
- **FML3 握手的实现细节**（改源码的人才需要看）：registry 快照/配方包/命令树在 minecraft-data 里不可解析 → protocol.json 里改为 `restBuffer` **裸透传**；应答包的 `messageId` 必须等于请求的 index。详见 `README.md` 与 `docs/logs/`。
- **`allow_insecure_coding`**：打开后 bot 能执行模型写的代码（本项目用它跑批量建造）。**这是明确的安全风险 —— 自己评估再开。**

### 让 bot "自主干活"要花多少钱（重要预期管理）

- **零成本**的自主行为只有 **`modes`**（自保 / 解卡 / 自卫 / 捡物 / 插火把 / 保持距离 / 张望）——**纯代码每 tick 跑，一次 API 都不调**。
- **要 LLM 自己"找活干"就必须有自主循环**（Mindcraft 的 `!goal` 之类），代价是**按冷却节奏持续调 API，token 消耗是持续的**。
- **两者不可兼得。** 想要"低消耗"就别开自主循环，改成**由外部定时器按需喂单次指令**（每次几百 token，频率可控）。

## 10. 语音链路

- **`voice_host=` 大多数情况留空**。
  只在**外网联机**且语音走穿透时才填 `<穿透域名>:<UDP远程端口>`。
  ⚠️ 本项目曾把它填成一个已经失效的地址，**结果所有人语音全挂**。改完必须实测。
- **SVC 不是双向透明**：bot 侧用的是 `mineflayer-simplevoice`，**必须与服务端 mod 同协议版本**（见 §1）。
- **TTS**：JS 版 edge-tts 已被微软 DRM 掐死（403）→ 用 **Python `edge-tts`**，且**做成常驻进程**（每次冷启动约 1 秒，久了很烦）。
- **STT**：`faster-whisper`，注意 `av` 版本（本项目锁 **14.2.0**）；无 CUDA 就老实 **CPU int8**（一句话 2~5 秒，零显存占用）。
- **音频编码**：Node 22 上 `@discordjs/opus` 没有预编译包 → 用 `opusscript` 纯 JS 实现替代（接口差异见 `README.md`）。
- **语音端口是 UDP**（24454），穿透要建 **UDP 隧道**，别只建 TCP。

## 11. 备份与恢复

| 事项 | 做法 |
| --- | --- |
| 备份时机 | **服务端停止后**再复制 `world/`。运行中直接复制会拿到撕裂的文件 |
| 备份前 | `save-all flush`，等日志出现 `All dimensions are saved` |
| 什么要备 | `world/`（含 `DIM-1` / `DIM1` / `playerdata` / `level.dat`）、`config/`、`mods/` 清单 |
| 恢复 | 整目录换回即可；`level.dat` 与 `level.dat_old` 是**成对**的，别只留一个 |
| 自动化 | 用计划任务每天凌晨停服窗口备份，**备份文件按日期命名**，保留 N 份 |

**关于 0 字节的 `.mca` 文件**：
在 `entities/`、`poi/` 里偶尔会出现 **0 字节**的区域文件。
**现象**：看着像损坏。
**结论**：这是"**预创建但从未写入**"的空区域占位，MC 读取时按"无数据"处理并会自行重建。
**处置**：**不要删。** 删除无收益、反增风险。

## 12. 故障速查表

| 现象 | 最可能的根因 | 处置 |
| --- | --- | --- |
| bot 连不上，`ECONNREFUSED`，且不自愈 | 服务端未就绪就启动了 bot | §8.4：先 RCON 确认就绪，再起 bot；必要时杀残留 `main.js` |
| 重跑启动脚本提示"已在运行"但 bot 其实不在 | 残留的 bot 主进程占着 8080 | 杀掉残留进程释放端口，再启动 |
| 语音所有人都不通 | `voice_host` 填了失效地址 | §10：清空后重启，再实测 |
| 语音单方不通 | 只放行了 TCP / 协议版本不匹配 | §1 版本映射 + §3 UDP 端口 |
| 悬挂实体 5 秒后消失、不留痕 | 坐标少加 1，实体被塞进墙里 | §6.1：支撑坐标 `+1+0.03125` |
| RCON 命令"没反应" | 忘了先发认证包 | §4.1：先发 id=1 / type=3 |
| 聊天栏被管理命令结果刷屏、bot 开始乱说乱动 | `sendCommandFeedback` 被打开 | §4.2：立即关掉；清理 bot 记忆文件里的噪音 |
| 服务端启动慢 5 分钟 | 外部下载（如汉化包 MD5 校验）阻塞 | §7.4：**等着**，别重启；功能不受影响 |
| 日志里一堆 ERROR | 多是 mod 联网检查失败 | §7.5：**归类后再判断**，别一口气全当真 |
| 远距离施工报 "position is not loaded" | 区块未加载 | §5：`forceload add` |
| "找不到 server.jar" | 那是 Forge，本就没有 | §2：用 `libraries/` + `win_args.txt` 启动 |
| 服务启动后一会儿就没了 | 进程托管/Job Object 回收 | §8.1：用受管理的后台任务或注册成服务 |
| 存档里出现 0 字节 `.mca` | 预创建未写入的空区域 | §11：**无害，别删** |
| `tasklist /fi` 查不到进程 | 该参数在某些环境失效 | §8.3：查全量列表；或用 psutil |
| 连服时 FML 握手警告 | 客户端与服务端 mod 列表不一致 | §1：对齐 mod 列表 |

## 13. 给 AI Agent 的协作规约

> **如果你是替人操作这套环境的 agent，请把本节当作硬约束。**
> 这些规则来自真实事故，不是形式主义。

### 13.1 硬规则（不可协商）

1. **不打开 `sendCommandFeedback`**（§4.2）。任何理由都不行，包括"为了排查"。
2. **不自作主张启停服务**。开服/关服是**使用者**的决定；除非被明确要求，不要启动或关闭任何服务，也不要让它常驻后台占资源。
3. **只动自己启动的进程**。结束进程前用「命令行 + 工作目录 + 监听端口」三者确认归属，尤其别误杀使用者自己开着的游戏客户端。
4. **破坏性操作必须"先列清单 → 说明影响 → 等确认"**：
   - 删除/覆盖**存档、配置、批量方块**之前，先给出**具体路径与数量**；
   - **先备份**，再说要改什么；
   - 有更安全的替代方案时**直接提出来**，不要盲目执行原指令。
5. **不可逆操作默认不做**：整目录删除、跳过校验的强制覆盖、批量改名 —— 除非使用者明确点头。
6. **不把密钥写进代码或仓库**。凭据走**环境变量**；发现密钥泄漏进日志/仓库要**立刻报告**并建议撤销。
7. **不确定就去查，不要猜**。版本号、端口、协议映射（§1）**不要凭记忆**——查文档、查日志、查 jar。

### 13.2 推荐工作方式

- **只读优先**：能靠"读日志 / 读存档 / 读配置"回答的，就**不要去改动系统**。
- **一次一个变量**：排障时**每次只改一处**再验证，否则分不清是哪个改动起的作用。
- **验证要看证据**：说"服务起来了"必须附 **端口状态 + RCON 应答**；说"建筑建好了"必须附 **存档直读或实时统计**。**截图不算证据。**
- **批量操作留痕**：把生成的命令**写成文件**再执行，可复现、可复核、可重跑。
- **如实汇报**：修好了说修好了；**没修好、有副作用、有未验证的部分，都要明说**，不要把"看起来像成功"讲成"成功"。
- **控制开销**：如果环境按 token/调用计费，**优先用确定性脚本，而不是让模型逐条试**。批量任务一次成型。

### 13.3 本仓库里可复用的确定性手段

| 需求 | 手段 |
| --- | --- |
| 批量下发命令 | 命令文件 + RCON 批量（`#` 为注释） |
| 验证建筑 | `save-all flush` 后**离线直读 `.mca`** |
| 数实体 | **实时计分板统计**（静态读存档在区块边界会重复计数） |
| 查地形高度 | 用 `execute if block` **二分探测**，别一格一格试 |
| 查进程/端口 | **psutil**（不要依赖 `tasklist /FI` 或 PowerShell 的 stdout） |
| 配置是否真的生效 | **写个脚本复现程序的配置合并顺序**，打印最终生效值 ——比"改完就当生效"可靠 |

## 14. 已知未解决 / 权衡项

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 汉化包更新导致的启动阻塞 | **不处理** | 属外部下载问题，功能不受影响，接受每次多等几分钟 |
