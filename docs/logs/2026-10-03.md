## 二、开服踩到两个新坑（一个外部、一个工具缺陷）

### 坑 1：启动被汉化 mod 阻塞约 5 分钟（外部因素）
- `I18nUpdateMod` 每次启动比对本地 / 远端汉化包 **MD5**，不一致就重下。当日三个包本地 md5 全部 ≠ 远端 → 逐个重下 → 该镜像站传输不稳 → 每包读取超时 **约 100 秒**，累计阻塞约 300 秒。
- **关键**：下载失败后 mod **自动回退使用本地旧包**，`Converting` + `Synchronized` 照常完成 → **功能不受损，纯属白等**。
- 对照排除：curl 请求该站返回 `HTTP 200 OK`（可达 ≠ 下载快）；系统代理未启用 → **不是代理干扰**。
- 可复现性：只要远端 md5 仍不匹配，下次开服还会重试；本地包与远端一致时只有 `Converting` 无 `Downloading`。

### 坑 2：守护脚本等待超时后盲目启动 bot（工具缺陷，已修）
- 现象：守护脚本等服务端只等 120 秒，超时后仍执行启动 bot → 此时服务端还在加载 → bot 连接被拒 `ECONNREFUSED` → mindcraft 报 **`Agent process exited too quickly and will not be restarted`（不自愈！）**。
- 更麻烦：`main.js`（MindServer）仍活着并占着 8080，再跑一次启动会被判"已在运行"跳过 → **必须先杀掉残留 `main.js` 才能重启 bot**。
- **修复（6 处）**：新增 PID 存活检测；就绪判据改为「端口监听 **且** RCON 能应答 `list`」、上限 120s → 600s；`start_server()` 超时后**不再放行去起 bot**；`start_bot()` 加「服务端未就绪则跳过」守卫；守护循环超时后**继续守着，服务端一就绪即自动补起 bot**。
- 回归脚本保留，改脚本后可复跑（只读探测，不启停服务）。

### 新踩的小坑
- 自写的极简 Python RCON 客户端在本机报 `WinError 10053`（本机软件中止连接），而 node 版同刻正常 → **本机 RCON 探测一律用已验证的 node 脚本，别临时手搓**。
- 长驻进程的后台任务 stdout 可能长时间不落盘，**不能靠它判断进度** → 看服务端日志时间戳与端口状态。

## 三、关闭服务端模组版本检查

服务端存在**两套**版本检查：

| 机制 | 来源 | 覆盖面 | 能否配置关闭 |
| --- | --- | --- | --- |
| Forge Version Check | `config/fml.toml` 的 `versionCheck` | 每次启动给 11 个模组逐个请求各自 `updateJSONURL` | ✅ 能 |
| Iron Furnaces Update Checker | mod 内 `ThreadUpdateChecker`（daemon 线程） | 只有 ironfurnaces 自己 | ❌ 硬编码，无配置项 |

- 改动仅 1 处：`config/fml.toml` 的 `versionCheck = true` → **`false`** → 11 个模组的版本检查全部不再执行（含把 `voicechat` 标 `OUTDATED` 的那条）。
- Iron Furnaces 的检查器扒字节码确认：直接 `openStream()` 拉 `raw.githubusercontent.com/.../updateVersions.properties`，**未读任何配置项**，关不掉；但它请求的域名本就拉不通（SSL 失败）→ 拿不到新版信息、不弹提示、不替换 jar，属"失败即止"，无害。它的 `[misc.misc] web` 开关挂在 **CLIENT** 配置，**服务端不加载**，改了无效。
- **重要事实**：**Forge 服务端从不自动下载 / 替换 `mods/*.jar`**。所谓"版本检查"只是联网查一下、打印一行提示，**不存在自动升级机制** —— 所以"保持当前版本"本来就是默认行为。
